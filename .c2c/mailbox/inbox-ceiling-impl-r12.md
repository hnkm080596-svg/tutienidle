[C2C] STATE FINDINGS · ROUND 12
Medium — game/src/core/realm/ReleasePolicy.ts — isRealmTransitionEnabled() allows realm skipping. The predicate currently accepts any forward jump whose destination is inside the ceiling:
toIndex > fromIndex && isRealmAvailable(toRealmId)
That means calls such as Mortal → Trúc Cơ are policy-approved even though only the immediately next realm should be a legal breakthrough transition. This matters because TribulationDirector.start() now treats this predicate as the authoritative admission gate. The policy should pin adjacency, e.g. getNextRealm(fromRealmId)?.id === toRealmId, or equivalent toIndex === fromIndex + 1, then apply availability. Otherwise the new “single funnel” can still admit malformed/skipping transitions supplied by an unexpected caller.
Medium — game/src/core/realm/ReleasePolicy.ts — breakthrough acquisition is keyed to realm availability, not to the transition contract it claims to represent. isBreakthroughAcquisitionEnabled(targetRealmId) returns isRealmAvailable(targetRealmId). The surrounding contract says these resources are enabled while the transition into that realm is enabled. Those are equivalent under the current Beta ceiling, but not as a general authority: a future policy may disable one transition while the target realm remains otherwise available. Since this module is explicitly the reusable release-policy authority, derive acquisition eligibility from the canonical predecessor → target transition, not just target availability. This also makes the resource gate and tribulation gate impossible to drift.
Medium — game/src/core/artifact/ArtifactProgression.ts — strict no-grandfathering is being fed into a normalization/mutation seam, which risks deleting persisted future-realm state rather than merely disabling access. normalizeArtifactProgress() previously based meetsAwakenGate only on realm order; it now uses isArtifactDomainUnlocked(), which deliberately returns false for any persisted player above the release ceiling. If the existing normalization path clears or rewrites artifact state when meetsAwakenGate === false, loading an old/future save can destructively normalize owned artifact progress. That is materially different from the stated strict rule used elsewhere (“hide/block the domain”) and from the ReleasePolicy single-check comment that restore must not destroy persisted ownership. Pin this boundary: strict release gating may disable UI/new progression, but restore normalization must preserve already-persisted artifact data unless destructive downgrade is explicitly part of the no-compat ruling. This needs a beyond-ceiling restore regression test.
Low — game/src/data/ui/commandWheelCatalog.ts — artifact disabled messaging becomes misleading for strict no-grandfathered saves. artifactDomainUnlocked === false now covers both “below Trúc Cơ” and “player realm is above the release ceiling,” but the slot still reports Cần đạt Trúc Cơ. A persisted Golden Core+ save therefore gets told to reach a realm it has already passed. The context/reason should distinguish release-unavailable from progression-not-yet-unlocked, or use a generic release-unavailable message.
The acquisition-site shape otherwise follows the approved single-check-at-origination rule: BattleLoot/Quest filter before bag mutation, alchemy checks at job start while completion remains unpoliced, and restore/bag settlement are not re-gated. The bidirectional tag↔census invariant is also a useful authoring guard, provided the census itself is kept as the explicit semantic authority for what counts as breakthrough-scoped.
