[C2C] STATE FINDINGS · ROUND 9
High — “all acquisition routes” is not satisfied by optional breakthroughRealmId tagging unless completeness is itself enforced. The spec makes release policy authoritative over breakthrough-scoped acquisition, but the executed plan adds an optional field only “where call sites allow.” Any future material/pill/recipe that is breakthrough-scoped but lacks the tag silently bypasses the policy. The spec should require either an integrity invariant/catalog test that every breakthrough-specific resource has a target realm, or an acquisition API where callers must supply the target realm explicitly. Optional metadata is acceptable for non-breakthrough resources; it is not sufficient as the sole authority for gated breakthrough acquisition.
Medium — the grandfathering contract is ambiguous, and isRealmAvailable(UNLOCK) && reached(UNLOCK) does not generally grandfather beyond-ceiling saves. If a domain unlock realm itself lies beyond the Beta ceiling, a restored player already beyond that realm will still fail isRealmAvailable(UNLOCK) and lose access despite having legitimately persisted progress. For the currently mentioned Foundation-unlocked domains this happens to work because Foundation is available, but the API is intended to be general. The spec should explicitly choose one policy: release ceiling always hides unavailable-domain features even from legacy saves, or persisted ownership/unlock state is grandfathered while new acquisition remains blocked. Do not describe the simple AND predicate as general grandfathering unless that is the intended rule.
Medium — unpoliced bag.add sites are safe only if the spec distinguishes reconstruction/fulfillment from acquisition authority. Restore should remain unpoliced: reloading persisted inventory must not destroy or reject already-owned future content. A settlement path is different unless it is strictly fulfillment of an acquisition decision that was already policy-checked when the reward was created. If settlement can originate or choose rewards independently, leaving it unchecked creates a bypass around the “ALL acquisition routes” requirement. Pin the invariant: policy is checked exactly once at reward eligibility/creation; persistence restore and deterministic delivery of an already-authorized reward must not re-check it.
Medium — TribulationDirector.start should be specified as the mandatory admission boundary, not merely assumed to be the single funnel. The plan is faithful only if every production route that starts tribulation reaches start() and no caller can directly initialize/advance the tribulation state. Because release-policy correctness depends on this being exhaustive, the spec should require a caller census or architecture test establishing that all tribulation admission flows pass through this method. Otherwise a later alternate entry point can bypass the ceiling while every predicate unit test remains green.
The central design is coherent: one release-policy module owning realm availability/transition/beyond-ceiling/breakthrough-acquisition decisions is preferable to deleting dormant KD+ content or maintaining domain-specific ceiling logic. Suppressing TC→KD admission while leaving Golden Core data authored also preserves the intended distinction between release gating and balance/content ownership.
