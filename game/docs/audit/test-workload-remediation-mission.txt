# FINAL REVIEW — TEST WORKLOAD REMEDIATION AFTER PR #36

Basis: PR #36 — Test Workload & Redundancy Audit.

The audit is accepted as sufficiently evidenced to proceed to remediation.

This mission supersedes the earlier assumption that the repository's 700+ test files are themselves the main performance problem.

## 1. Final conclusion from PR #36

Current default Vitest workload:

    777 files
    7,268 executed case-instances
    ~307.7 s median wall time

The test suite is NOT broadly slow.

Measured evidence shows:

    PerfectionEconomy.test.ts      ~296.7 s
    EssenceSubstitutionEconomy      ~8.7 s
    TrucCoJourney                    ~5.0 s

while the overwhelming majority of the remaining suite is individually cheap.

In particular:

    GameManager.* family
      101 files
      572 cases
      ~4.0 s

    TurnBattleSystem* family
      48 files
      358 cases
      ~1.4 s

Therefore:

**Do NOT perform a broad GameManager/TurnBattleSystem consolidation for performance reasons.**

Reducing physical file count is a maintainability concern, not the current workload bottleneck.

# 3. Fix the 483 accidental duplicate executions

PR #36 identified an execution-graph defect.

Two eager globs import test modules as data modules, causing their tests to register and execute again.

Fix:

    game/tests/architecture/statDomainWhitelist.test.ts

Its include root is:

    ../../src/data/**/*.ts

Therefore its exclusion must correspond to that same root:

    !../../src/data/**/*.test.ts

Do NOT accidentally use:

    !../../data/**/*.test.ts

for this file.

Also fix:

    game/src/core/stats/StatCalculator.theTu.test.ts

with an exclusion corresponding to its data root, e.g.:

    !../../data/**/*.test.ts

Use the existing glob-negation pattern in:

    LegacySkillCoverage.test.ts

as repository precedent.

Expected result:

    -424 accidental registrations
    -59 accidental registrations

Total:

    -483 duplicate executions

All affected tests must continue to execute exactly once from their canonical test files.

Verify this through Vitest enumeration/reporting rather than assuming the glob change is correct.

Add a small stable regression guard if one can prevent this class of eager-glob test registration without introducing significant framework complexity.

Do not overengineer it.

# 4. Reclassify PerfectionEconomy correctly

`PerfectionEconomy.test.ts` is not an ordinary regression suite.

It currently contains two semantically different classes of tests.

## A. Cheap analytic/invariant tests

Keep these in the normal regression gate.

They protect contracts such as:

    mortalStatBudget
    reachableStatSourceCensus
    no unintended stat source
    expectedEssencePerKill
    expectedKillsForBody

These are cheap and valuable during normal development.

## B. Full driven economy simulations

The tests invoking:

    measureNormalRun(...)
    measurePerfectionRun(...)

are long-horizon balance simulations.

They include:

    canonical normal measurement
    perfection full-accounting run
    deterministic repeated seed
    safety-bound simulation
    three-seed measurement
    normal/perfection cross-run consistency

These simulations are valuable.

DO NOT delete them.

DO NOT weaken them.

DO NOT reduce their seed coverage merely to make the default suite faster.

Instead, move them out of the normal development regression gate into an explicit:

    BALANCE SIMULATION GATE

---

# 5. Use two primary concepts, not unnecessary tier complexity

For the current project, prefer:

## REGRESSION GATE

Purpose:

    fast code → test → fix feedback

Contains:

    unit tests
    contracts
    invariants
    architecture tests
    QA regressions
    adversarial tests
    cheap integration tests
    cheap PerfectionEconomy analytic tests

This should remain the normal/default Vitest command.

Target after remediation:

    approximately 55–60 seconds

Exact measured result is authoritative.

## BALANCE SIMULATION GATE

Purpose:

    validate long-horizon economy/progression behavior

Contains the expensive driven PerfectionEconomy simulations.

Provide an explicit command such as:

    npm run test:balance

or an equivalent repository-consistent name.

The balance suite must remain first-class and easy to run.

Do NOT implement it using `it.skip`, commented tests, or otherwise-disabled tests.

The tests must be executable through an explicit command.

It SHOULD be run when changes affect:

    spirit-stone economy

    stage rewards

    breakthrough requirements
    stat-source availability

    beta/release preparation

Do not require a ~5-minute economy simulation after unrelated changes such as:

    UI layout

    VFX

    unrelated component refactors
