# TASK — FULL TEST WORKLOAD & REDUNDANCY AUDIT

Repository: Tiên Hiệp Idle  
Scope: entire current repository / current HEAD.

## Objective

Audit the accumulated test system to determine how much **real test workload** can be removed or made cheaper **without weakening behavioral coverage, architectural protection, regression protection, or invariants**.

The repository has accumulated roughly 700+ Vitest test files over many development missions and QA rounds.

This task is NOT primarily about reducing physical file count.

The actual objective is to reduce:

- executed test cases;
- duplicated semantic coverage;
- repeated expensive setup;
- repeated GameManager construction;
- repeated battle simulations;
- repeated save/restore cycles;
- unnecessarily expensive integration tests;
- tests that are already strictly subsumed by stronger canonical tests;
- tests unnecessarily executed in the default development gate.

A reduction such as:

777 files → 400 files

is NOT considered an improvement if approximately the same workload still executes.

The metrics that matter are:

1. executed test cases;
2. wall-clock execution time;
3. expensive runtime/setup operations;
4. semantic/invariant coverage retained;
5. default-gate workload;
6. full-suite workload.

# 4. SEMANTIC REDUNDANCY AUDIT

This is the core of the mission.

For every major multi-test family, determine whether tests are:

### UNIQUE

Protect a behavior/invariant not equivalently protected elsewhere.

### OVERLAPPING

Share some semantic coverage but each still contains unique assertions.

### STRICTLY SUBSUMED

Every meaningful behavior/assertion protected by test A is already protected by test B or another canonical suite at equal or stronger boundaries.

Only STRICTLY SUBSUMED tests may become `SAFE_DELETE`.

Similarity of setup or test names is NOT subsumption.

Example:

A tests:

    level 18 allows hidden breakthrough

B tests:

    levels 1..18 satisfy hiddenBreakthrough === level >= 18

If B exercises the same production authority and same relevant state boundary, A may be strictly subsumed.

But if A additionally verifies:

    persisted hidden flag
    emitted event
    no currency mutation

then B does NOT subsume A unless those properties are also asserted.

Document the proof.

# 7. ARCHITECTURE TESTS

Audit architecture tests separately.

These often have low runtime but high protection value.

Prefer KEEP when a test enforces a distinct law such as:

- import direction;
- write authority;
- projection ownership;
- dependency boundary;
- domain whitelist;
- runtime ownership.

Do not consolidate architecture laws merely to reduce file count.

However, identify:

- duplicated source scans;
- duplicated filesystem traversal;
- duplicated parser work;
- repeated compilation/parsing that could share infrastructure.

Classify performance improvements separately from semantic deletion.

# 8. PLAYWRIGHT / E2E

Audit Playwright separately.

# 9. PROPERTY / INVARIANT REPLACEMENT

Find groups of example-based tests that can be replaced by a stronger invariant/property test.

- realm mappings;
- grade mappings;
- cost/debit laws;
- resource conservation;
- deterministic RNG;
- save round-trip equivalence;
- stat composition;

A property replacement is acceptable only when it protects all relevant semantics of the examples.

Keep historically important concrete regression examples when they provide useful boundary documentation or exercise a distinct path.

Do not use property tests merely to reduce test count.

# 10. DEFAULT GATE VS FULL SUITE

Not every valuable test necessarily needs to run in every local/default gate.

Classify tests into possible execution tiers:

## TIER A — FAST DEFAULT

Must run continuously.

Examples:

- unit contracts;
- invariants;
- architecture laws;
- high-value regression tests;
- cheap integration tests.

## TIER B — INTEGRATION

More expensive subsystem scenarios.

Run in appropriate CI/pre-merge gate.

## TIER C — EXHAUSTIVE / ADVERSARIAL

Large matrices, fuzz/property stress, exhaustive simulations, historical stress cases.

Run in full CI/nightly/manual QA where appropriate.

Important:

Moving a test out of the default gate does NOT mean deleting it.

The full suite must remain available.

Recommend tier movement only when the feedback-speed benefit is meaningful.

---

# 11. REQUIRED CLASSIFICATION

Every candidate optimization must use exactly one of these categories:

### KEEP_DEFAULT

Unique/high-value protection and appropriate cost.

### SAFE_DELETE

Strictly semantically subsumed.

Must provide the exact surviving test(s) that cover every relevant assertion/invariant.

### MOVE_OUT_OF_DEFAULT_GATE

Valuable test, but unnecessary for every default run.

State recommended tier.

### REWRITE_CHEAPER

Invariant should remain, but current test exercises too much runtime.

State:

- current expensive path;
- proposed cheaper authority/seam;
- why coverage remains equivalent.

### STRUCTURAL_MERGE_ONLY

Files/setup can be consolidated for maintainability, but this does NOT materially reduce runtime.

Do not count this category toward workload reduction.

# 16. VALIDATION STANDARD

A proposed optimized suite must still detect all known classes of failures protected by the current suite.

For high-value proposed deletions, perform mutation-style validation where practical:

Temporarily introduce or simulate a representative defect locally and confirm the surviving test fails.

Do NOT commit these mutations.

Examples:

- change a gate boundary;
- remove a debit;
- allow duplicate settlement;
- change deterministic ordering;
- skip restore reconciliation;
- emit the wrong combat event.

This is particularly important when claiming that a broad/property test subsumes historical regression tests.

---

# 17. IMPORTANT DISTINCTION

Do not confuse:

    fewer files

with:

    less workload.

Example:

    48 files / 400 cases
    ->
    10 files / 400 cases

is primarily a maintainability improvement.

Report it as:

    STRUCTURAL_MERGE_ONLY

unless measured runtime proves otherwise.

The primary success criterion is:

    LESS EXECUTED WORK
    WITH EQUAL OR STRONGER PROTECTION.
