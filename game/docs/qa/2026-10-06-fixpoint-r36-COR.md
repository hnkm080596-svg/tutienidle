## Verdict

**PASS WITH EVIDENCE — 0 Critical / 0 High / 0 Medium / 1 Low / 2 Nit.**

All five headline r35 claims verify against the code and hold under probe. The `onResume` arm set is exactly four reachable shapes (`same`, `replaced`+save+ok, `replaced`+save+rejected, `replaced`+no-save — the last unreachable by construction since `CloudSaveLoadResult` `'ok'` requires `save` and `reconnectPipeline` mints `replaced` only with the payload attached); only `replaced`&&save&&ok pays the discard, strictly after the restore returns and strictly before `resumeSimulation` — synchronous, no interleavable early-return between them, and the unlatch provably lands on an already-stopped clock. The per-battle minted set is cleared symmetric except the two documented session-lifetime fields (`turnBattleSystem`, `combatRng`), and every reader of the newly-cleared trio is `undefined`-guarded. The fallback gate evaluates liveness at fire time; the re-mint race is *impossible* because every teardown path (`discardInFlightBattle`, `abandonBattle`, cycle entry) funnels through `clearPendingSteps`, which `clearTimeout`s all armed fallbacks and wipes `pendingStepDone` wholesale — probed. The step-7 snapshot→stop→start→re-freeze→`syncOffScreenFreeze` order is correct, including the stale-`'not-revealed'` correction — probed both directions.

Nothing found that changes behavior for real players. The three entries below are a trivial memory pattern the new gate introduces, and two pre-existing/edge asymmetries worth keeping on record.
