# QA wave-7 (r6) blind seam hunt — aggregate state, 2026-10-11

Base: `a4d7e59a` (devin/khai-mach). Scope: the six aggregate seams the
orchestrator listed after waves 1-6 (roll-seed allocator vs enqueue
order, parallel orders + unit progress, digest vs rollSeedBase,
qualityAccum mean-band, ThienCo dormant jobs[0], migration chain +
journal pending).

## Confirmed defects

### R6-D1 — HIGH — dormant parked order counts against the authored slot law at the save gate

Cross-system seam (5 + 2): three authorities disagree about what a
parked dormant-family order is.

- `AlchemySystem.tick` parks scope-hidden records forever but keeps
  them in `this.jobs` (pinned mechanism, AlchemyQueueSeams.qa.test.ts).
- `startJob` deliberately does NOT count dormant records against live
  slots ("a restored dormant job may not occupy the live slot").
- `buildGameSave` serializes the UNFILTERED feed:
  `alchemyJobs: detachSaveValue(gameManager.alchemySystem.getJobs())`
  (SaveSystem.ts).
- `validateGameSaveShape` counts EVERY persisted record against the
  slot law: `alchemyJobs.length > maxJobs -> refuse`
  (saveShapeValidation.ts ~4625).

Result: a player whose pre-scope-lock save carried an in-flight
non-beta order restores it parked, then fills the authored live slots
normally. The writer persists `[dormant, live x maxJobs]`, and the
gate refuses that save on the next load — an honest save self-bricks
into the recovery surface, same failure signature as the wave-6
R5-SEED-WEDGE fix.

Fix direction (either): writer emits only slot-occupying records, or
the slot count filters to records that can settle pills
(scopeHiddenPillFamilyOfId(recipeId) === null).

Repro: `src/core/alchemy/AlchemyDormantSlotGate.qa.test.ts` —
`[dormant + live]` at a level-1 pill_room must validate (RED on HEAD);
two-live-job pin stays refused.

### R6-D2 — MEDIUM — ThienCo entry + building badge narrate a parked dormant order as live brew

`useThienCoEntries` reads `alchemyJobs[0]` and
`getBuildingStatus('pill_room')` returns 'active' on
`getAlchemyJobs().length > 0` — both against the same unfiltered feed.

- Dormant-only queue: badge 'active', entry emits `done 0/1, con 1
  phut` forever — a stale deadline clamps to a phantom one-minute
  countdown for an order that can never settle.
- `[dormant, live]` queue: the entry narrates the parked order's
  frozen progress and stale deadline while the real order brews
  invisibly behind it, and `waiting` counts the parked record as a
  queued live order.

Fix direction: the entry/badge must read only slot-occupying (live)
orders — same filter R6-D1 needs.

Repro: `src/components/home/ThienCoAlchemyDormantEntry.qa.test.ts` —
two tests, both RED on HEAD.

### R6-D3 — MEDIUM — save gate dedupes jobId but not rollSeedBase across jobs

`validateAlchemyJobsSave` carries a `seenJobIds` set (F-ALCH-JOBID-DUP:
"two persisted jobs sharing one id can only be a replayed record")
but no `seenBases` equivalent. Two jobs with distinct jobIds sharing
one `rollSeedBase` pass every per-job check and are accepted — yet no
honest writer can emit that pair (`allocRollSeedBase` hands out
disjoint strides; the merge path never mints a second record). On the
next tick both orders roll unit i off seed `base + i` — one stream
window serves two deliveries, defeating the anti-scum anchor the base
exists for. Crafted-save class (digest is publicly foldable), but the
same class the gate already refuses for jobId — a coverage gap, not a
philosophy difference.

Fix direction: `seenBases` dedupe in `validateAlchemyJobsSave` for
entries that carry `rollSeedBase`.

Repro: `src/core/alchemy/AlchemyRollSeedBaseDup.qa.test.ts` — dup pair
at a level-3 room must refuse (RED on HEAD); distinct bases still
validate (pin, passes).

## Seams investigated and refuted

- **Seam 1 (allocator vs enqueue order)** — distinct bases guaranteed:
  `rollSeedCursor` only advances by `ALCHEMY_MAX_BATCH_QUANTITY`
  strides per `startJob`; two enqueues in one tick allocate two
  disjoint strides (a merge extends the tail order within its own
  stride, never a second base). Cancel releases nothing into cursor
  space in-session (cursor is monotonic — paid-reroll trade, intended),
  and the cancelled stride is only reissued post-restore once its
  record is gone (anti-scum replay-safety holds). Honest-player
  cross-order collision: impossible. Crafted-save collision: R6-D3.
- **Seam 2 (parallel orders + unit progress)** — `tick` settles each
  job independently (`unitsProcessedAt` per job, deadline positions
  cumulative from `startedAtMs`); `drainSettlementEvents` returns
  events FIFO in `jobs[]` order with per-job `jobDone` flags — no
  path assumes array-order completion. A later order finishing first
  is spliced correctly. The only array-order consumer is the ThienCo
  `jobs[0]` read — covered by R6-D2. Restore shift re-stamps
  `startedAtMs`/`completesAtMs` by a uniform delta; relative order
  preserved.
- **Seam 3 (digest vs rollSeedBase, both job shapes)** —
  `alchemyJobReservationDigest` folds `seedField` only when
  `rollSeedBase` is defined and `batchFields` only when `quantity` is
  defined; the same function is the single fold at every site
  (startJob stamp, merge re-fold, tick-advance re-fold over the
  written state, restore re-derive, verify replay), so legacy
  no-base and seeded records both verify. Ordering in
  `validateAlchemyJobsSave` (base-domain check before reservation
  replay) is cosmetically irrelevant — issues accumulate, both
  surface. A stripped-base forged record cannot replay the digest.
- **Seam 4 (qualityAccum mean-band)** — the persisted gate refuses
  count < 1 / non-integer count / non-finite or negative sum / mean
  outside [count, 2*count] per entry, and `integrityIssues` refuses
  accum on completed meridians and out-of-line meridian ids. In-memory,
  `recordMeridianOpenQuality` keeps count >= 1 (early return on empty
  spend) and `delete accum[meridianId]` on completion — the fold can
  never persist an entry beside a completed meridian. `sum=NaN`
  requires an ItemQuality outside `PILL_QUALITY_EFFECT_UPLIFT` (typed
  map — unreachable from the pill pipeline). The fold's NaN-slips-
  through-`Math.min/max` case needs corrupted in-memory state only —
  documented residual, not a save-layer defect.
- **Seam 6 (migration chain + journal pending)** —
  `migrateSaveToCurrentVersion` (null/undefined/array-guarded, chain
  88 -> flatten -> 89 -> re-stamp -> 90) is invoked at all four gates:
  local boot, SAVE_READY pull, `adoptCommittedPending`, file import.
  `adoptCommittedPending` additionally binds
  `record.schemaVersion === foundVersion` BEFORE accepting the
  migrated payload, then runs the same shape + acceptance pipeline —
  a journal record stamped by an older build is upgraded, not
  refused, and a version-mismatched envelope is incompatible, not
  corrupt. Unknown/missing/future versions fail closed to
  `incompatible`.
