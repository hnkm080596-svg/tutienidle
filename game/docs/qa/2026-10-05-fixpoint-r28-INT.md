## Findings

### QA-2026-10-05-R28-INT-1 — persistPlayer's data-refuse escalation is a dead write that leaks a stale armed `'corrupted' + 'remote'` card into later error mounts

- **Severity: Medium** — Status: **Confirmed** (probes M1, M2, M3 + source chain)
- **Where:** `src/App.vue:575-595` (persistPlayer refuse arm) vs the mount gate `src/App.vue:1204-1211` (`SaveIncompatibleScreen` inside `RouteMount v-else-if="entryStage === 'error'"`).
- **What disagrees:** every other `saveIssue.report` site pairs the report with the transition that mounts the surface — boot commit arm (useAppLifecycle.ts:568 + `boot.fail()` :569), firstSave arm (:691 + :700), onResume reject (App.vue:704 + `bootFlow.fail()` :705, whose comment states the rule: *"report() alone is a dead write and would leak a stale status into later boots"*). The persistPlayer arm calls `report()` and returns — under `entryStage === 'game'` the card cannot mount, so the "remote-reset affordance that unwedges the row" the comment advertises is never reachable in-session.
- **Concrete consequence chain (deterministic):**
  1. Autosave refuse (e.g. `OUTGOING_ADMISSION_REJECTED`) → `saveIssue.report('corrupted', payload, undefined, 'remote')` under remote authority → `remoteResettable` derives `true` (probe M1).
  2. The live consequence is only `authorityState → 'recovery'` (overlay + acknowledge→sign-out; probe M3). `saveIssue.status` is never cleared by a subsequent successful save — `clear()` has no production caller (probe M2: status+scope survive an `ok` write).
  3. Any later `bootFlow.fail()` arm that does NOT itself report — generic load failure (useAppLifecycle.ts:389-394), creation-grant throw (:622), non-coded firstSave refuse (:700) — transitions `entryStage → 'error'` and mounts `SaveIncompatibleScreen` carrying the stale `corrupted` status, the stale payload, and the armed `'remote'` scope → `handleReset` offers `resetCharacter()` against a remote row nothing in that boot proved unhealthy.
  4. Provenance inversion: the armed codes only fire when the adapter was never invoked (`saveCalls === 0` — the remote row provably holds the last-good commit), while server refuses that could mean "the write already landed" (SERVER_ERROR bucket: CHECKPOINT_*/CUTOFF_REGRESSION/MUTATION_ID_REUSED) are deliberately left unarmed. The pending-conflict arm passes `'local'` for exactly the "remote row is the healthy head" reasoning (useAppLifecycle.ts:426-429) — the persistPlayer arm applies the opposite label to the same fact pattern.
  5. Under LOCAL mode the arm is strictly worse: no authority overlay AND no mount — the advertised "card is the only surface" is dead too; the user gets one deduped autosave toast and nothing else while every write refuses.
- **Why Medium:** contract disagreement between sibling report sites (the onResume arm documents the pairing rule the persistPlayer arm violates); the stale armed card can offer the destructive remote reset on a provably-healthy row after a transient/healable refuse or an unrelated boot failure. Reachable mechanism chain; user-confirmed destruction, so not High. The r27-INT report's verified-consistent entry ("mounts over the running game") was an incorrect claim about this same gate — the defect predates this commit but was never visible.

### QA-2026-10-05-R28-INT-2 — `restoreJobs` shift arm re-derives the digest over the UN-normalized reservation: the malformed-input throw the r27 fix closed in the clone arm still fires one arm upstream

- **Severity: Low** — Status: **Confirmed** (probes I1, I2, I3)
- **Where:** `src/core/alchemy/AlchemySystem.ts:391-398` — `digest: alchemyJobReservationDigest(shifted, job.reservation)` folds `job.reservation.specialIngredients.map(...)` on the RAW reservation before the normalize arm (:405-411, `Array.isArray(...) ? map : []`) runs.
- **What disagrees:** for `startedAtMs > restoreNowMs`, the identical payloads the clone arm now tolerates throw `TypeError` through the digest fold: `specialIngredients:{}`, `reservation: null`/`{}`/`42` all throw; only `reservation === undefined` is skipped by the shift guard and tolerated — an intra-arm inconsistency on top of the sibling-arm one (probe I2). The same malformed reservation on a non-post-dated job normalizes cleanly to `[]` (probe I1) — one function, opposite verdicts on one field.
- **Reachability (why Low):** every gated seam refuses this shape first — `verifyAlchemyJobReservation` names `'specialIngredients'` pre-digest and the shape validator refuses the wire (probe I3); only ungated callers reach `restoreJobs` with it (the `EarlyGameSession.restoreCheckpoint` test seam, direct `saveOps.restoreFromSave` callers), and `restoreGameSession`'s catch converts the throw to a denied `'rejected'` restore (probe I3). Deny-direction, bounded — but it is the exact throw class r27-INT-Low/r27-AUT-2 was believed to close, and the arm's own comment promises "the normalize arm must never throw on an ungated payload."

## Fixpoint assessment

The correction set is internally coherent at every gated seam: one validator serves both write and read gates (identical verdicts and envelopes), `restoreClockMs` re-grounds all four deadline channels in the save epoch while accrual stays on the authority epoch, the armed refuse set maps cleanly onto the terminal authority arms, the fail-closed wrapper is consumed uniformly by all six call sites, and cap ordering is consistent with sibling validators.

The two open items are both integration-level leftovers rather than policy errors: a `report()` site that does not observe the mount contract its siblings document (Medium — offers a remote reset against a healthy row via stale state, and silently no-ops under local mode), and one digest fold that reads the raw reservation before the tolerance fix can run (Low — unreachable through gated seams, deny-direction). No granting, wedging, or silent divergence found.
