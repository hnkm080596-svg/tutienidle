## F-INT-12-01 — Low — `DecomposeSystem.settleOffline` fast-forwards an unbounded window on a crafted `offlineSinceMs`

- **Class**: REAL_DEFECT — sibling of the r11 crafted-marker batch, one field over: `settleNowMs` (window END) was clamped to `Date.now()` (`GameManagerSaveRestore.ts:396-399`) but `offlineSinceMs` (window START) still passes `save.player.lastSavedAt` raw (`:400`).
- **Mechanism** (SOURCE_PROOF): `DecomposeSystem.ts:286-297` computes
  `windowStartMs = Math.max(nextCycleAt - cycleMs, Math.floor(offlineSinceMs), nowMs - PRODUCTION_OFFLINE_CAP_SECONDS * 1000)`
  then runs `while (this.nextCycleAt <= windowStartMs) this.nextCycleAt += this.cycleMs` — **no bound**. With a finite-but-astronomic `lastSavedAt` (e.g. `9e15`, passes `isFiniteNumber` at `saveShapeValidation.ts:2215`), `windowStartMs` adopts it and the loop iterates `(9e15 - 1.7e12) / 30000 ≈ 3×10^11` times — effectively forever, inside the synchronous `restoreGameSession` try block. A hang is not a throw: no `'rejected'`, no `boot.fail()`, no recovery surface; the offending cloud row is sticky, so every subsequent boot wedges identically.
- **Trigger chain**: requires `elapsedOfflineSeconds > 60` to open the settle block (`:403`). Under the legacy/undefined authority branch this is impossible — a future `lastSavedAt` yields `calculateOfflineTime` elapsed `0` (`GameClock.ts:84-91`, `currentTime = max(lastOnlineAt, ts)`), gate closed. Under `cold-boot` (`useAppLifecycle.ts:458-468`), elapsed derives from the SERVER window `untilMs - sinceMs` where `sinceMs = serverAuthority.cutoffMs ?? lastSavedAt ?? serverNowMs` — a row with a real `progression_cutoff_at` makes elapsed independent of the crafted marker → gate opens → hang. `live-replacement` always passes `elapsed=0` (`:437` only arms the farm re-anchor) → unreachable there.
- **Reachability today**: remote-authoritative deployment + a crafted save payload + the row carrying a server cutoff. In current beta the whole path is further gated — `isScopeHidden('equipmentOreDecompose')` returns `0` before the loop (`betaFeatureFlags.ts:41` = `false`; `DecomposeSystem.ts:276-278`). **Latent**, same class r11 rated Low for `lastDailyResetAtMs` (flag-off in beta). It arms the day the flag flips and costs nothing to bound (`windowStartMs` could also cap `Math.min(offlineSinceMs, nowMs)` — same clamp already applied to `settleNowMs`).
- **Sibling sweep**: production lanes are bounded differently — `advanceWorkerLanes` drains by `budgetMs` (`ProductionOffline.ts:156-169`) and treats `offlineSinceMs` as `emptyLaneStartMs` (a future start yields zero spawned cycles, underpay only). Alchemy consumes only `settleNowMs` (`:454-463`). Decompose is the sole unbounded consumer.

## F-INT-12-02 — Low — `player.lastSavedAt` is both an editable payload field and the validator's trusted ceiling

- **Class**: REAL_DEFECT — same un-clamped root as 12-01, opposite direction: instead of flowing raw into a settle window, it gates which payload rows the shape validator calls "impossible".
- **Mechanism** (SOURCE_PROOF): the validator rejects `appliedAtMs > lastSavedAt` (`:1484-1489`), `expiresAtMs > lastSavedAt` (`:811-812`), `workerCycles[].startedAtMs > lastSavedAt` (`:3334-3337`), and `alchemyJobs[].startedAtMs > lastSavedAt` (`:3567`), with matching reads at `:4258`, `:4305`, `:4377`. A crafted `lastSavedAt` far in the future turns every one of these checks vacuous — rows stamped "after the save" that validation exists to reject now pass.
- **Impact bound**: downstream witnesses still gate real mints (F-ALCH-JOB-FORGE reservation verification at `AlchemySystem.ts:605` fails forged jobs closed; worker-cycle deadlines decide on their own `advanceWorkerLanes` math) — the residue is admitted forged records, not demonstrated free loot. But the check's stated contract ("activation after save is impossible") is silently conditional on an editable field — exactly the trust-boundary inversion the r11 batch was closing elsewhere. Note `player.restoreFromSave` self-heals the marker: `store.lastSavedAt` is overwritten by `Date.now()` on the next autosave (`stores/player.ts:246`).
- **Direction**: same fix family as `settleNowMs` — clamp the marker to `now` before the impossibility comparisons, or validate it against the server envelope under remote authority.

## F-INT-12-03 — Low — the consumed-anchor retry guarantee is unpinned at the assembled level (and residue is asymmetric)

- **Class**: COVERAGE_GAP — the r11 fix is correct (verified below), but its retry-safety is produced by an implicit cross-module contract that no assembled test pins.
- **Chain**: `restoreGameSession` order is `player.restoreFromSave` → `setActivePlayer` → `saveOps.restoreFromSave` (`SaveSystem.ts:293-297`). If the player-slice guard ever re-applies the payload — a `$reset`-style change, WeakMap keyed differently, whitelist refactor — the persisted anchor returns and the whole window re-pays: F-INT-11-02's exact defect, silently back, and every existing green test still passes.
- **Coverage status**: `fixpointR11IntEvidence.qa.test.ts` drives `autoFarmOps.settleAutoFarmOffline` directly on a live player (the anchor mechanics in isolation — sound). `GameManagerSaveRestore.onceOnlySettle.test.ts` pins double-restore convergence but never exercises throw→retry through `restoreGameSession`. The missing pin is an assembled one: `restoreGameSession(save)` with a post-settle slice throwing, then `restoreGameSession(save)` again → assert single settle/pay. **No test was added** because pinning a forced throw inside `saveOps.restoreFromSave` requires reaching into private deps — the seam exists (monkey-patching the thrown slice) but the pin belongs to whoever owns the restore harness; flagged as the single highest-value coverage add.
- **Residue asymmetry (recorded, not separately rated)**: on that same retry, player-resident mints from attempt-1 (the `idleSkillInsightDaily` ledger) survive the player no-op, while bag-resident mints are wiped by `materialBag.clear()`/`pillBag.clear()`/`equipmentBag.clear()` (`:236-238`) and rebuilt from the payload — the daily insight quota stays consumed for loot that never lands. ## F-INT-12-04 — Nit — `drawFromPool` non-finite rng still falls through to the last entry (fail-open sibling)

- **Class**: EDGE — the r11 throw covers non-finite `total` (weights) but not non-finite `rng()`: `roll = NaN * (total + missWeight)` stays `NaN` through `roll -= entry.weight`, no `roll <= 0` ever fires, and the fall-through at `:106` pays `pool[pool.length - 1]` on an ungated table — precisely the silent-last-entry behavior the throw just closed for weights. On a gated table (`missWeight > 0`) the same NaN silently reads as a miss.
- **Reachability**: none in honest production — the loot stream is `Math.random` (`BattleLootSystem.ts:175`) or the `setLootRng` seam (`GameManager.ts:1104`, used by `EarlyGameSession.ts:215` benchmarks and tests); neither `mulberry32` nor `Math.random` yields NaN on valid input. Same verdict as the weight throw itself: a wiring/data defect tripwire, fail-closed would just need `!Number.isFinite(roll)` beside the total check.
- **Related blast-radius note (recorded)**: a `drawFromPool` throw inside a live-battle `processDefeatedEnemies` (`GameManagerBattleRewardOps.ts:107`) leaves earlier enemies' mints applied and the batch unrecorded in `rewardsGranted` — the next tick re-processes the same enemy and throws again, so the failure is a per-frame crash loop, not a one-shot. Intended fail-closed direction, dormant on authored data; recorded so a future data defect isn't mistaken for an update-loop bug. In the autofarm/restore path the throw propagates to `restoreGameSession`'s catch → `'rejected'` → recovery surface — handled correctly.
