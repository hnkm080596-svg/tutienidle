## Findings

### F1 — Medium — `TribulationDirector.start()` silently destroys a pending committed outcome
- **Location:** `core/tribulation/TribulationDirector.ts:216-218` (guards) and `:260` (`this.committedOutcome = null`).
- **Evidence:** `start()` refuses only when `getCooldownSeconds() > 0 || this.active` (217). It then unconditionally clears `committedOutcome` (260). The committed outcome is the domain's once-only settlement record — `commitOutcome` stamps it once at the terminal transition, `serializeRuntime`/`restoreRuntime` persist it (including a bound-or-null receipt and `cooldownUntil`), and `settleOutcome` (`core/tribulation/TribulationOutcomeService.ts:144-176`) is the single site that applies consequences and binds the receipt. `useTribulation.checkTribulationOutcomeAction` (`composables/useTribulation.ts:149-241`) settles every tick and is the only drain path (`director.clear()`). Neither `GameManager.startTribulation` nor `triggerBreakthroughAction` consults `getCommittedOutcome()`.
- **Expected:** per the module contract, a committed outcome "stays pending until `clear()` drains the run"; a new `start()` while one is pending should refuse.
- **Actual:** `start()` wipes the pending record before its consequences ever land.
  - Restored **victory** (receipt unbound, `active=null`, no cooldown) → `start()` passes its guards → realm advance, talent entitlement, foundation/first-entry rewards never apply; a subsequent defeat would even charge defeat penalties over the destroyed win.
  - Restored **defeat** (receipt unbound): cooldown delays the wipe, but once `cooldownUntil` expires, `start()` clears the record → cultivation loss, spirit-stone loss, and the Kiep Thuong debuff never apply (`resolveDefeat`, `TribulationOutcomeService.ts:379-422`).
  - In-session: a Quan Khi (mortal→qi_refining) victory settles to `realmEntered: null` while holding `pendingTalentEntitlement`; the player is still mortal so `isRealmTransitionEnabled` and `canTriggerBreakthrough` stay open — a scripted/early `startTribulationPrepared` call inside the hold window hits the same clobber. (Post-victory foundation holds are coincidentally protected only because the golden_core transition is release-closed — the gate, not a pending-outcome check, covers them.)
- **Repro (proof chain):**
  1. `director.restoreRuntime({ committedOutcome: { attemptId, outcome: 'victory', targetRealmId: 'foundation_establishment', grade, breakthroughType: 'normal', receipt: null, settlementError: null }, cooldownUntil: 0, active: null })` — the exact shape `serializeRuntime` emits when a save lands between `commitOutcome` and the first settle tick.
  2. `director.getCommittedOutcome()` → the pending victory, consequences never applied.
  3. `director.start(player, stats, hasTrucCoDan, 'foundation_establishment')` → guards pass (`cooldown=0`, `active=null`, transition enabled, chapters exist) → line 260 nulls the record, new active run minted.
  4. `getCommittedOutcome()` → `null`; the earned victory is gone. Fix is a one-line pending-outcome refusal at the top of `start()`.

### F2 — Low — Realm-gate fail-open on unknown `requiredRealmId` (quests + stages)
- **Location:** `core/quest/QuestSystem.ts:48-54` (`isUnlocked`), `core/game/GameManagerCatalogOps.ts:272-290` (`isStageUnlocked`).
- **Evidence:** `getRealmIndex` returns `-1` for unknown ids. `isUnlocked` computes `getRealmIndex(player.realmId) >= getRealmIndex(quest.requiredRealmId)` — a typo'd/retired `requiredRealmId` resolves to `-1`, so `playerRealmIndex >= -1` is true for every player (and a corrupt `player.realmId` also `-1` passes). `isStageUnlocked` has the same shape: `playerRealmIndex < requiredRealmIndex` fails only when required is a valid index below the player's; required `-1` → `playerRealmIndex < -1` never true → realm gate silently passes. NodeSystem fail-closed this exact case per T8-75 (`requiredIndex < 0 → console.warn + return false`, `core/progression/NodeSystem.ts:64-70`); the quest/stage gates never received the same treatment — an inconsistent ruling for the same defect class.
- **Actual:** an authored-data typo in `requiredRealmId` silently unlocks content for all realms.
- **Expected:** unknown prerequisite realm → fail closed (matches NodeSystem's ruling).
- **Reachability:** all authored values today are valid (`mortal`, `qi_refining`, `foundation_establishment`, `test_realm` fixtures), so no live trigger — this is a data-drift hazard, hence Low.
